# Этап 3: Паттерн Адаптер (Абстрагирование платформы)

Цель: Достижение платформенной независимости (Platform Agnostic) кодовой базы
путем изоляции специфичных для среды API от ядра приложения. Стек: TypeScript
Interfaces, Паттерн Adapter/Bridge, Vite Environment Variables.

## 3.1. Проектирование контракта платформы (IBridge.ts)

- Действие: Создание директории src/bridge/ и объявление строгого интерфейса
  IBridge.
- Спецификация: Описание сигнатур для трех основных системных подсистем:
  - storage — типизированные методы get<T> и set<T> для персистентного
    хранения.
  - http — метод request, принимающий объект настроек и возвращающий
    Promise<HttpResponse> (абстракция над сетевыми запросами).
  - clipboard — асинхронный метод writeText для работы с буфером обмена.

## 3.2. Реализация провайдера для Userscript (MonkeyBridge.ts)

- Действие: Создание реализации интерфейса IBridge для браузерных расширений.
- Маппинг:
  - Вызовы storage маппятся на GM_getValue / GM_setValue.
  - Вызовы clipboard используют GM_setClipboard (с фоллбэком на
    navigator.clipboard).
  - Вызовы http.request оборачивают callback-ориентированный
    GM_xmlhttpRequest в стандартный Promise, стандартизируя обработку
    ответов и ошибок.

## 3.3. Реализация провайдера для Desktop (TauriBridge.ts)

- Действие: Создание реализации интерфейса IBridge для среды Tauri.
- Маппинг:
  - Вызовы storage маршрутизируются в локальную файловую систему через
    @tauri-apps/plugin-store.
  - Вызовы clipboard используют @tauri-apps/plugin-clipboard-manager.
  - Вызовы http.request транслируются в нативный метод fetch из
    @tauri-apps/plugin-http, позволяющий обходить браузерную политику CORS.

## 3.4. Маршрутизация реализаций (Точка входа Bridge)

- Действие: Создание индексного файла src/bridge/index.ts.
- Логика: Использование статического анализатора Vite (import.meta.env.MODE
  или VITE_PLATFORM) для определения целевой среды сборки. На этапе компиляции
  (build-time) экспортируется нужная реализация (TauriBridge для десктопа,
  MonkeyBridge для браузера), исключая попадание лишнего кода в итоговый бандл
  (Tree-shaking).

## 3.5. Рефакторинг слоя бизнес-логики

- Действие: Тотальная замена всех прямых обращений к функциям GM_* в
  директориях src/api/, src/core/ и src/features/ на вызовы методов
  глобального объекта Bridge.
- Сетевой слой: Рефакторинг функций запросов (например, anilistQuery,
  fetchShiki). Код очищается от вложенных коллбеков (onload, onerror),
  переводится на синтаксис async/await и обработку исключений через try/catch.

## 3.6. Абстракция бизнес-логики переноса (Sync Service)

- Выделение логики загрузки списков (fetchShikimoriListV2, syncShikiToAlList) в независимый сервис.
- Настройка маршрутизации запросов: в среде браузера запросы идут через стандартный fetch (используя куки текущей сессии Shikimori), а в среде Tauri — через Bridge.http (анонимные запросы на уровне Rust, обходящие CORS, но требующие соблюдения пункта 2.7 об открытом профиле).

Итог Этапа 3: Модули бизнес-логики и UI полностью изолированы от среды
выполнения. Кодовая база теперь может собираться под любой таргет без изменения
исходного кода ядра. Улучшена читаемость сетевого слоя за счет перехода на
Promise-архитектуру.
