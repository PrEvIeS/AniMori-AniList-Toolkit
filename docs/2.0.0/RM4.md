# Этап 4: Сборка Desktop-приложения (Интеграция Tauri 2.0)

Цель: создание независимого исполняемого файла для Windows с внедрённым скриптом
на базе единой кодовой базы, обход сетевых ограничений браузера и обеспечение
нативного UX. Стек: Tauri 2.0, Rust, WebView2, Vite Environment Modes.

> Актуализировано на старте Этапа 4 (31 июля 2026):
> целевая платформа только Windows, macOS и Linux из плана убраны;
> контракт `IBridge` и обе реализации моста готовы с Этапа 3, писать их заново не нужно.
>
> Почищено 1 августа 2026 по итогам живой эксплуатации:
> пункт о заголовках CSP вычеркнут как не подтвердившийся;
> реклама и всплывающие окна плеера сведены в один пункт 4.7;
> инсталлятор и автообновление вынесены в предрелизный блок в конце документа.

## Порядок работ

Сначала закрывается всё, без чего приложением невозможно пользоваться каждый день
(пункты 4.1–4.7), и только потом — упаковка и доставка (предрелизный блок).
Причина простая: инсталлятор и автообновление имеют смысл только для готовой версии,
а настраивать их раньше — значит перенастраивать потом.

## 4.1. Инициализация рабочей среды Tauri — выполнено

- Директория `src-tauri`, идентификатор `com.foulnike.animori`, версия 2.0.0,
  библиотека `animori_lib`.
- `Cargo.toml`, `Cargo.lock` и файлы npm-манифеста коммитит разработчик локально.

## 4.2. Интеграция системных плагинов — выполнено

- `plugin-http` (сеть мимо страницы), `plugin-store` (файл настроек),
  `plugin-clipboard-manager` (буфер обмена), `plugin-opener` (внешние ссылки).
  Плагин `log` подключён только в отладочной сборке.
- Крейты прописаны в `Cargo.toml`, плагины зарегистрированы в билдере:
  без регистрации вызовы из `TauriBridge` падают на исполнении, а не на компиляции.

## 4.3. Инъекция скрипта и создание окна — выполнено

- Окно строится кодом в `src-tauri/src/lib.rs`, а не описывается в конфигурации:
  ему нужен внешний адрес `https://anilist.co/home` и два скрипта инициализации.
- Скрипт и стили вшиваются через `include_str!`; стили идут первыми, иначе
  интерфейс мелькает неоформленным.
- Строка CSS прогоняется через сериализатор JSON, а не склеивается вручную.

## 4.4. Политики безопасности (Capabilities) — выполнено

- `capabilities/default.json`: окно `main`, доступ из контекста `anilist.co`.
- Allowlist сети по фактическому списку источников `src/api`: `graphql.anilist.co`,
  `shikimori.io`, `shikimori.rip`, `smotret-anime.online`, `anime365.ru`,
  `api.animethemes.moe`, `raw.githubusercontent.com`, `kodik-api.com`.
- Разрешения плагинов: `store:default`, `clipboard-manager:allow-write-text`.
  Фоллбэка у буфера нет намеренно — отсутствие разрешения должно падать громко.
- **Собственные команды тоже требуют явного разрешения** (`allow-animori-reload`,
  `allow-animori-open-external`) — выяснилось живым запуском, а не из документации.

## 4.5. Desktop UX и системная интеграция — осталась память окна

- Выполнено: маршрутизация ссылок (внутренние остаются в окне, внешние уходят
  в браузер через `plugin-opener` с проверкой схемы), перезагрузка, блок навигации
  с клавиатурными сочетаниями, надёжность записи настроек, ускорение старта.
- Осталось: `@tauri-apps/plugin-window-state` — сохранение и восстановление
  геометрии окна между запусками.
- Отложено до запроса: боковые кнопки мыши Back/Forward. Стрелки в блоке навигации
  и Alt+← / Alt+→ закрывают ту же потребность.

## 4.6. Оркестрация процесса сборки — выполнено

- Два режима Vite: `--mode userscript` и `--mode tauri`. Алиас `@bridge-impl`
  подтягивает нужную реализацию моста; прикладной код импортирует его только
  как `@/bridge`.
- Контроль: после каждой правки конфигурации сборки замерять число модулей
  и размер обеих сборок. Пакеты `@tauri-apps/*` в бандле юзерскрипта означают,
  что алиас обойдён.

## 4.7. Реклама и всплывающие окна плеера (объединён с прежним 4.11)

Две части одной задачи: реклама в плеере Kodik бьёт с двух сторон — окнами по клику
и врезками внутри фрейма. Оба случая решаются в Rust и управляются одним
тумблером настроек, поэтому держать их раздельно смысла нет.

### А. Перехват всплывающих окон

- Обработчик `on_new_window` в Rust-бэкенде.
- Если блокировка включена — попытки фрейма открыть стороннее окно пресекаются.
  Если выключена — новое окно уходит в системный браузер.
- Источник значения — ключ `set_block_popups` (поле `blockPlayerPopups`).
  Бэкенд читает его через мост, а не хранит своё состояние.

### Б. Сетевой блокировщик уровня оболочки (условная часть)

- Зачем отдельный уровень: реклама живёт внутри фрейма чужого происхождения,
  куда DOM-блокировщик из `src/features/adblock` не дотянется в принципе.
- Как: перехват `WebResourceRequested` через COM-интерфейсы WebView2
  (крейты `webview2-com` и `windows`) и решение о блокировке через крейт
  `adblock` (движок Brave) с набором фильтров EasyList.
- Чего это не даст: преролл, приходящий с того же CDN, что и видео,
  фильтрами не снимается вовсе. Ожидания стоит строить сразу с этим знанием.
- Открытые вопросы к моменту взятия в работу: способ поставки баз фильтров
  (вшивание через `include_str!` против файлов в ресурсах), обновление баз,
  атрибуция лицензии CC BY-SA.
- Связь с DOM-блокировщиком: `src/features/adblock` остаётся как есть и продолжает
  работать в юзерскрипте. Сетевой уровень его дополняет, а не заменяет.
- Управление: тот же единственный тумблер, без отдельных переключателей.

## Снято с плана

### Модификация CSP-заголовков (бывший пункт 4.8)

Предполагалось, что заголовки `Content-Security-Policy` от AniList помешают входу
в аккаунт и загрузке фреймов Kodik, и их придётся ослаблять перехватом
`on_web_resource_request`.

**Живым запуском не подтвердилось** (1 августа 2026). Вход в аккаунт в десктопной
сборке проходит ровно так же, как в браузере, плеер загружается и играет.
Запросы к API идут через процесс оболочки мимо страницы, поэтому политика
содержимого их не касается. Пункт закрыт без единой строки кода.

Сам перехват ответов остаётся возможным инструментом, но если он понадобится —
то ради пункта 4.7Б, а не ради CSP.

## Предрелиз: упаковка и доставка

Оба пункта берутся в работу максимально поздно — непосредственно перед выпуском
версии. До того момента разработчик собирает приложение локально.

### П. 1. Сборка Windows-инсталлятора в CI (бывший 4.10)

- Workflow `.github/workflows/release.yml`, запуск по тегу с версией.
- Два артефакта: `animori.user.js` для GreasyFork и `AniMori_Setup.exe` (nsis)
  для GitHub Release.
- Сборки под macOS и Linux из плана исключены.

### П. 2. Система автообновлений (бывший 4.9)

- Плагин обновлений Tauri, опрос GitHub Releases при запуске.
- Зависит от предыдущего пункта: обновлять нечем, пока инсталлятор
  не публикуется автоматически. Брать раньше — значит переделывать.

## Итог Этапа 4

Приложение работает автономно от браузера, корректно интегрируется в ОС
(открытие ссылок, управление окном, перезагрузка, навигация), не подвержено
внешним блокировкам сети и делит 100% бизнес-логики с версией для браузера.
Нативный инсталлятор и автообновление — предрелизный блок.
