### 1.3 Кодировка: как я испортил три файла

Перемещать файлы через API GitHub нельзя — в наборе инструментов нет операции
переименования, а перезаливка трёхсот килобайт журналов это ровно та операция,
которая однажды уже оборвалась на середине. Поэтому весь перенос был отдан
владельцу скриптом для консоли, а я его составил.

В скрипте извлечение исторических файлов было записано так:

```
git show <sha>:<path> | Out-File -Encoding utf8 <target>
```

**Это ломает кириллицу.** Windows PowerShell 5.1 не передаёт байты git
напрямую: он декодирует поток кодовой страницей консоли (cp866), получает
мусор, и уже мусор записывает в UTF-8. Простое перенаправление через `>`
портит точно так же. Я предупредил владельца только про BOM, а про перекодировку
самого потока не подумал. Три файла — `STAGE-1.md`, `STAGE-1-FULL.md`
и `STAGE-2-3.md` — уехали в `6dcafe4` нечитаемыми. Заодно git выдал три
предупреждения про замену CRLF на LF: перезапись через консоль подменила ещё
и переводы строк.

Правильный способ — не пропускать содержимое через консоль вообще:

```
git checkout <sha> -- <path>
git mv <path> <target>
```

`checkout` пишет байты в рабочий каталог сам, консоль в цепочке не участвует.
Предупреждения про CRLF при этом тоже исчезли.

Восстановление закоммичено как `6e39cd7`. Проверка сделана по размеру
объектов в индексе, а не на глаз: `git cat-file -s` дал 30 097, 51 161
и 86 868 байт — точное совпадение с исходными объектами. Совпадение размера
до байта означает, что восстановлено ровно то, что лежало в истории.

**Урок.** Любая передача содержимого файла через конвейер PowerShell — это
перекодировка. Если файл не ASCII, проверять надо не глазами по первым
строкам, а сравнением размера с исходным объектом.

## 3. Автообновление: разбор механизма

Предрелизный блок `RM4.md` ставит автообновления пунктом П.2 и отмечает,
что разбор надо начинать с объяснения механизма, а не с кода. Ниже разбор.
Работы ещё не начаты; это план, а не отчёт.

Скрипта тема не касается вовсе: у него канал обновлений давно есть, Greasy
Fork рассылает новую версию по метаданным `update.greasyfork.org/scripts/572948`.
Речь только о десктопе.

### 3.1 Почему это надо решить до релиза

Апдейтер Tauri проверяет подпись установщика публичным ключом, **вшитым
в бинарник на момент компиляции**. Если 2.0.0 выйдет без ключа и без адреса
манифеста, то ни один установивший её пользователь не сможет обновиться
автоматически никогда — только скачать следующую версию руками. Пользователей
у нас пока ноль, так что цена ошибки сегодня минимальна и растёт с каждым днём
после релиза. Владелец выбрал полный вариант в составе 2.0.0.

### 3.2 Из чего состоит

- Два плагина: `tauri-plugin-updater` и `tauri-plugin-process`. Второй нужен,
  чтобы перезапустить приложение после установки.
- Пара ключей подписи, генерируется `npm run tauri signer generate`. Публичный
  идёт в `tauri.conf.json`, в `plugins.updater.pubkey`. Приватный и пароль
  к нему — в секреты репозитория, `TAURI_SIGNING_PRIVATE_KEY`
  и `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`. В репозиторий приватный ключ
  не попадает ни при каких условиях, и копия его хранится отдельно: потеря
  ключа означает новую версию с новым публичным ключом и ручную переустановку
  у всех.
- Манифест `latest.json` со ссылкой на установщик и его подписью. Отдельный
  сервер не нужен: адрес вида `.../releases/latest/download/latest.json`
  всегда указывает на последний нечерновой релиз. Файл генерирует релизный
  workflow.
- Разрешения в `src-tauri/capabilities/default.json`: `updater:default`
  и `process:allow-restart`.

### 3.3 Порядок работ

Апдейтеру нечего проверять, пока автосборка не начнёт выкладывать установщик,
подпись и манифест. Значит, П.1 из `RM4.md` — не параллельная задача,
а обязательный первый шаг.

В workflow важен порядок команд сборки: `emptyOutDir: !isTauri` означает, что
юзерскриптовая сборка чистит `dist/`, а тауриная — нет. Сначала `build`,
потом `build:tauri`, иначе первая снесёт артефакты второй. Это уже записано
в части 4, пункт 7.1, и здесь повторено, потому что именно в CI ошибка
будет незаметной.

### 3.4 Подводные камни, замеченные заранее

- **Pre-release.** Релиз, помеченный предварительным, в `latest` не попадает.
  Апдейтер такое обновление просто не увидит.
- **Двойная версия.** Сейчас `2.0.0` записана и в `package.json`,
  и в `tauri.conf.json`. Tauri умеет читать версию из `package.json`, если
  в поле `version` указать путь к нему. Тогда при выпуске правится одно место,
  и невозможна рассинхронизация, при которой установленное приложение считает
  себя новее вышедшего обновления.
- **Режим установки NSIS.** Из трёх вариантов — тихо, с полосой прогресса,
  полный визард — для обновления разумен средний: пользователь видит, что
  процесс идёт, но ничего не нажимает.
- **Проверить можно только вживую.** Убедиться, что механизм работает,
  получится не раньше, чем будут опубликованы два релиза подряд.

### 5.1 Релизный workflow

Коммит `9ca032a`, новый файл `.github/workflows/release.yml`. Каталога
`.github/` в репозитории не было вовсе — автосборка создана с нуля.

Триггер — push тега вида `v*`. Раннер `windows-latest`: цель сборки одна,
NSIS, и собрать её больше негде. Разрешение `contents: write` нужно, чтобы
действие могло создать релиз и загрузить в него файлы.

Порядок шагов: checkout → Node 20 с кешем npm → стабильный Rust →
`swatinem/rust-cache` с `workspaces: src-tauri` → `npm ci` → `npm run build` →
`tauri-apps/tauri-action`.

Порядок двух сборок здесь не случайность, а прямое следствие
`emptyOutDir: !isTauri` (см. 3.3). Юзерскриптовая сборка чистит `dist/`,
поэтому идёт первой. Тауриную запускать отдельным шагом не надо: её выполнит
`beforeBuildCommand` внутри самого действия, то есть после `npm run build`
в любом случае.

Кеш Rust экономит около минуты на сборку и не влияет на результат: ключ кеша
считается по `Cargo.lock`, и добавление зависимости его инвалидирует.

### 5.2 Имя установщика: поправка к решению владельца

Владелец выбрал «переименовывать в `AniMori_Setup.exe` в workflow». Здесь
я внёс поправку, и она была принята молчаливо, без возражений.

Переименовать основной артефакт нельзя. `latest.json` генерируется тем же
действием и ссылается на файл по тому имени, которое дал ему Tauri.
Переименование основного файла оставляет в манифесте ссылку на несуществующий
адрес, и апдейтер ломается ровно в тот момент, когда он впервые понадобится.

Принятая схема: основной установщик остаётся `AniMori_2.0.0_x64-setup.exe`,
на него смотрит апдейтер; рядом в тот же релиз кладётся **копия** с коротким
именем `AniMori_Setup.exe` — для людей и для ссылки в README. Копию делает
отдельный шаг на `pwsh`, затем `softprops/action-gh-release` дозаливает в тот
же тег её и `dist/animori.user.js`.

Копия безопасна: подпись считается по содержимому файла, а не по его имени.
Один и тот же байт-в-байт установщик под двумя именами проходит проверку
одинаково.

### 5.3 Конфигурация

Коммит `dfa4ac9`, `src-tauri/tauri.conf.json`.

- `bundle.createUpdaterArtifacts: true` — включает выпуск `.sig` рядом
  с установщиком.
- `plugins.updater.pubkey` — публичный ключ, отпечаток `C7F3ECF6395D43DF`.
- `plugins.updater.endpoints` — единственный адрес
  `https://github.com/foulnike/AniMori-AniList-Toolkit/releases/latest/download/latest.json`.
- `plugins.updater.windows.installMode: "passive"` — полоса прогресса без
  вопросов, как и решено в 3.4.
- `version` переехала на `"../package.json"` — устранена двойная версия
  из 3.4. Теперь номер живёт в одном месте, и приложение не может счесть себя
  новее вышедшего обновления.

**Важный порядок:** `createUpdaterArtifacts` без ключа роняет сборку на этапе
подписи, поэтому оба параметра добавлены одним коммитом, ни один раньше
другого.

Побочное следствие для разработчика: локальная `npm run tauri:build` теперь
требует в окружении `TAURI_SIGNING_PRIVATE_KEY`
и `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`. Без них сборка падает. Это не поломка,
а работа подписи.

### 5.4 Расхождение с планом: обновление ведётся из Rust

Пункт 3.2 предписывал два плагина (`updater` и `process`) и два разрешения
в `capabilities/default.json` (`updater:default`, `process:allow-restart`).
**Сделано иначе, и это сознательное отступление.**

Разрешения в capability нужны только для вызова команд плагина **из
JavaScript**. Единственное окно приложения открыто на `anilist.co`, и в
`remote.urls` стоит именно этот домен. Выдать туда `updater:default` значит
позволить любому скрипту чужого сайта запустить загрузку и установку
исполняемого файла на машину пользователя. Это худшее разрешение из всех,
какие можно выдать окну на внешнем URL.

Поэтому весь процесс уведён в Rust:

- новый файл `src-tauri/src/updater.rs` (коммит `69b3e0d`);
- `capabilities/default.json` **не изменён ни на строку**;
- плагин `process` не понадобился вовсе: перезапуск делает `app.restart()`,
  метод ядра Tauri, а не плагина. В `Cargo.toml` его нет.

Логика та же, что уже принята в проекте для `window-state` и `opener`: плагин
регистрируется, командам из JS доступ не выдаётся, наружу торчит только своя
проверенная команда — а здесь и её нет.

План задним числом не правится; расхождение зафиксировано здесь.

### 5.5 Поведение обновления

Модуль `updater.rs`:

- проверка запускается фоновой задачей **последней строкой** `setup()`, уже
  после создания окна. Сетевой запрос прямо в `setup()` задержал бы появление
  окна на время ответа GitHub, а при мёртвой сети — на весь таймаут
  соединения;
- нет сети, недоступен GitHub, отбит фаерволом — запись в журнал уровня WARN
  и молчание. Окон не появляется;
- версия совпадает — запись INFO, ничего больше;
- есть новее — родной диалог с номером новой и текущей версии и списком
  изменений из описания релиза. Список обрезается до 600 символов: системное
  окно Windows не прокручивается, и длинное описание вылезло бы за экран.
  Кнопки «Установить» и «Позже», отказ пишется в журнал;
- ошибка установки — запись ERROR и окно с текстом ошибки и советом скачать
  установщик вручную;
- успех — запись INFO и `app.restart()`.

Диалог показывается через `blocking_show`, и это безопасно **только** потому,
что весь модуль живёт в фоновой задаче. Тот же вызов на главном потоке
заморозил бы цикл событий и повесил окно вместе с самим диалогом. Если код
когда-нибудь переедет в синхронный контекст — переписывать на неблокирующий
вариант обязательно.

Прогресс загрузки никуда не выводится: своего интерфейса у оболочки нет,
а рисовать его поверх чужого сайта мы сознательно не стали. Полосу покажет
сам установщик благодаря `installMode: passive`.

### 5.7 Проверка сборкой

Локальная сборка владельца после всех четырёх коммитов:

| Что | Результат |
| --- | --- |
| `npm run typecheck` | чисто |
| `npm run build` (юзерскрипт) | 72 модуля, 616.60 КБ, gzip 145.75 |
| `npm run build:tauri` | 82 модуля, JS 563.69 КБ (gzip 135.02), CSS 46.76 КБ (gzip 8.56) |
| Cargo | 34 новых пакета, релизная сборка 1 мин 12 с |
| `AniMori_2.0.0_x64-setup.exe` | 4 737 042 байта |
| `AniMori_2.0.0_x64-setup.exe.sig` | 416 байт |

Размеры бандлов не изменились ни на байт: вся правка легла в Rust, фронтенд
не тронут.

Появление `.sig` — доказательство того, что подпись работает и что пара ключей
сходится с паролем. Разрешились и версии плагинов: `tauri-plugin-updater`
2.10.1, `tauri-plugin-dialog` 2.7.2, из зависимостей приехал
`minisign-verify` 2.5 — тот самый проверяльщик подписи.

Файла `latest.json` при локальной сборке нет и быть не должно: его собирает
только `tauri-action` в CI.

**Чего проверка НЕ доказывает.** Того, что обновление действительно доедет
до пользователя. Установленная 2.0.0 сравнивает себя с манифестом последнего
релиза, и пока в `latest` лежит она же, диалог не появится. Первая настоящая
проверка возможна только после второго тега.

### 5.8 Ключи: что теперь нельзя терять

Приватный ключ лежит у владельца вне репозитория, пароль к нему —
непустой. Секреты `TAURI_SIGNING_PRIVATE_KEY`
и `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` заведены в настройках репозитория.

Потеря пары или пароля не чинится обходным путём: следующая версия уйдёт
с новым публичным ключом, и все, кто успел поставить 2.0.0, обновятся только
руками. Ключ и пароль подлежат хранению в двух местах.
