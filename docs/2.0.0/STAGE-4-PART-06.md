# Этап 4, часть 6. Предрелизная ревизия и авария AniList

Дата записи: 2 августа 2026, вечер. Ветка `desktop-dev-4`.

## 0. Зачем новая часть

Часть 5 остановилась на готовом автообновлении и успешной локальной сборке
подписанного установщика. Дальше пошла предрелизная ревизия, и за один вечер
случилось столько, что дописывать это в конец части 5 нельзя: файл уже под
тридцать шесть килобайт, а прошлый опыт говорит, что журнал начинает рваться
при полной перезаписи ближе к пятидесяти. Поэтому продолжение вынесено сюда.

В этой части: чистка документов перед выпуском, описание релиза из CHANGELOG,
избавление от второго места хранения номера версии, инцидент с преждевременным
тегом и, главное, авария 2 августа — AniList отключил публичный API, и это
вскрыло в переводчике горячую петлю.

## 2. Описание релиза берётся из CHANGELOG

Коммит `3b6eabcd`, файл `.github/workflows/release.yml`.

До этого тело релиза на GitHub оставалось пустым, и содержимое выпуска
приходилось бы вписывать руками после каждой публикации. Добавлен шаг `notes`

`releaseBody`.

Там же в шапку файла вписан блок «ВАЖНО ПРО ОТМЕНУ» — причина в разделе 3.

## 3. Инцидент: преждевременный тег

При выдаче инструкции по выпуску команда постановки тега была подана вместе с
остальными, без выделения того, что она необратима. Тег `v2.0.0` был поставлен и
отправлен раньше, чем закончилась ревизия.

Дальше владелец удалил тег локально и на сервере. Прогон workflow к этому моменту
уже шёл, и по завершении он **пересоздал удалённый тег** и опубликовал релиз
`v2.0.0` со всеми пятью артефактами. Скачиваний не было, релиз и тег удалены,
список тегов проверен: вершина снова `v1.9.1`.

Два урока, оба записаны в шапку `release.yml`:

1. Тег — последнее действие выпуска и только по явному подтверждению.
2. Отмена выпуска начинается с кнопки Cancel во вкладке Actions. Удалять тег,
   пока прогон жив, бессмысленно: сборка создаст его заново.

## 4. Номер версии хранится в одном месте

Коммит `70f804cb`, файл `vite.config.ts`.

Версия юзерскрипта была прописана в шапке `vite.config.ts` строкой, при том что
настоящий источник — `package.json` (на него же смотрит `tauri.conf.json`).
Два места означали, что рано или поздно они разойдутся и пользователь получит
обновление с прежним номером. Теперь `vite.config.ts` читает `package.json`
через `readFileSync` и подставляет `version` в шапку.

## 5. Авария 2 августа: AniList отключил API

### 5.1 Что произошло

Во время финального теста собранного приложения журнал за несколько секунд
забился доверху. `graphql.anilist.co` отвечал **HTTP 403** с телом:

> The AniList API has been temporarily disabled due to severe stability issues.
> Please check the announcements channel in the official AniList Discord for
> more information.

Причина внешняя, к нашему коду отношения не имеет. Но реакция приложения на неё
оказалась негодной.

### 5.2 Диагноз: горячая петля

В журнале это выглядело так: пачка из тридцати пяти тайтлов падает, следом
тридцать пять записей «неудач подряд 38, ключ отпущен», сразу за ними те же
тридцать пять «Cache MISS», через полторы секунды всё повторяется с цифрой 39.
Два запроса в секунду, бесконечно.

Механизм оказался такой:

1. `anilistQuery` ставил паузу **только на 429**. Любой другой не-двухсотый код,
   включая 403 и всю пятисотую группу, просто бросал ошибку без торможения.
2. `processMediaBatch` ловил её и возвращал всю пачку через `requeue`.
3. `requeue` снимает с элементов страницы маркер `dataset.queued`.
4. Обход DOM через триста миллисекунд видит те же карточки как новые, кладёт их
   в очередь, `scheduleDispatch` через полсекунды запускает такую же пачку.

Защита `MAX_ATTEMPTS` здесь не работает в принципе: она считает попытки по
ключу, а ключ после «отпускания» создаётся заново вместе со свежим узлом
страницы. Счётчик в логе дорос до 39 именно потому, что ключи пересоздавались.

Важно понимать: 403 был лишь поводом. Ровно то же самое случилось бы при аварии
шлюза (502, 503) или при пропаже интернета.

Побочный ущерб: кольцевой буфер журнала рассчитан на тысячу записей, и такая
петля смывает его начисто меньше чем за минуту. То есть в момент реальной
проблемы пользователь остаётся без диагностики.

### 5.3 Отступ в клиенте AniList

Коммит `ffca67ba`, файл `src/api/anilist.ts`.

Добавлено:

- `isServerFailure(status)` — отказом источника считаются 403, 408 и всё от 500
  и выше;
- `backOffAfterServerFailure()` — растущая пауза: 30 секунд, дальше удвоение при
  каждом следующем отказе, потолок 15 минут. Успешный ответ обнуляет серию и
  пишет в журнал INFO о том, что источник ожил;
- та же пауза ставится при транспортном сбое (нет сети);
- запись в журнал делается **только в момент входа в отступ**, а не на каждый
  отказ — иначе лекарство ничем не лучше болезни;
- в начале запроса проверяется остаток паузы: больше десяти секунд — вызов
  отклоняется сразу, а не висит обещанием четверть часа;
- новый экспорт `anilistPauseRemaining()`.

Ветка 429 оставлена как была: у неё свой `Retry-After` и свой лимит повторов.

### 5.4 Очередь спит до конца паузы

Коммит `bdf90f8`, файл `src/features/translator/index.ts`.

Проверка лимитов в `processTransQueue` будила очередь раз в секунду. При
пятнадцатиминутной паузе это девятьсот записей WARN — журнал смывается ровно
так же, как в самой аварии. Теперь ожидание считается по остатку паузы:

```ts
const wait = Math.max(1000, anilistPauseRemaining()) + Math.floor(Math.random() * 500)
```

### 5.5 Инцидент при записи файла через API

Отдельно, как урок. Правка `src/features/translator/index.ts` отправлялась через
API полной перезаписью (патч-инструмента нет), и содержимое **оборвалось на
середине** функции `processPersonBatch`: вместо примерно сорока килобайт в ветку
легло тридцать. Коммит `dfbc54d` нерабочий.

Восстановление заняло одну команду:

```
git checkout ffca67ba -- src/features/translator/index.ts
```

после чего две правки были внесены вручную в редакторе. Целостность файла в ветке
проверена чтением целиком: шапка, все функции, концовка с `translateNode` и
`debouncedFindContent` на месте.

Правило на будущее: крупные файлы (от тридцати килобайт) через API целиком не
отправлять. Либо точечные правки руками в редакторе, либо разбиение файла.

### 5.6 Проверка результата

Сборка после исправлений: typecheck чист, юзерскрипт 72 модуля, 618.15 КБ.

Поведение при лежащем AniList по журналу от 20:46:

- 20:46:38 — один запрос, в ответ 403, запись «AniList отвечает 403: запросы
  приостановлены на 30с (отказов подряд: 1)»;
- 20:47:08 — ровно одна повторная попытка, пауза выросла до 60 секунд, «отказов
  подряд: 2»;
- записей «неудач подряд» нет ни одной, счётчики попыток не тратятся.

Было около ста восьмидесяти запросов за полторы минуты, стало два. Задача
закрыта.

### 5.7 Что осталось незакрытым

По решению владельца эти два хвоста отложены: они не мешают работе, а полное
отключение API у AniList случается редко.

1. **Повторные промахи внутри паузы.** `requeue` снимает `dataset.queued`,
   поэтому обход DOM возвращает те же карточки в очередь и пишет по сорок строк
   «Cache MISS» на каждый цикл отступа. Лечится тихим возвратом в очередь
   (вернуть id в `pending`, не трогая маркеры) в ветке, где источник в паузе.
2. **Несколько будильников.** Каждое пробуждение очереди во время паузы ставит
   свой `setTimeout`. В логе видно два WARN подряд с разным остатком (28284 и
   27844 мс). Лечится единственным таймером сна: если он уже стоит — выходить
   молча.

Оба места и предполагаемые правки описаны здесь специально, чтобы вернуться к
ним без повторного разбора.

## 6. Состояние на момент записи

Вершина `desktop-dev-4` содержит всё перечисленное. Тега `v2.0.0` нет, последний
выпущенный релиз — `v1.9.1`. Приложение собирается и подписывается локально,
установщик проверен.

Перевод названий сейчас не работает по внешней причине: пока AniList держит API
выключенным, проверить его вживую невозможно. Проверено только поведение при
отказе, и оно правильное. Остальные части приложения (списки, экспорт, свои
виджеты, адблок) на 403 не реагируют и работают.

Следующий шаг — выпуск: тег ставится последним действием и только по явному
подтверждению, после него `animori.user.js` заливается на Greasy Fork вручную,
CI туда не публикует.
