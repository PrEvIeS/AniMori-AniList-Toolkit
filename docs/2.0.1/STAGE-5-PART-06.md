## 5.3.7 — аварийный выход при мёртвом прокси

### Зачем

Щуп из 5.3.4 ловит опечатку в порте и выключенный клиент. Прокси, который
принимает соединение, но не выпускает трафик, щуп проходит — и окно остаётся на
странице ошибки вместе с панелью настроек. Тот же кирпич, другая причина.

### Что сделано

Сторож страницы: если через 12 секунд после создания окна бандл не отметился,
а прокси был применён (`Applied`), показываем родной диалог с предложением
выключить прокси и перезапуститься. Отказ не меняет ничего.

Файлы:

| Файл | Что |
| --- | --- |
| `src-tauri/src/proxy_guard.rs` | Новый модуль: `PageReady`, `animori_page_ready`, `spawn`, `disable_proxy` |
| `src-tauri/src/proxy.rs` | `current_status()` — исход и адрес для сторожа; снос переменной окружения |
| `src-tauri/src/lib.rs` | `mod proxy_guard`, команда в `generate_handler!`, `spawn()` после создания окна |
| `src-tauri/build.rs`, `capabilities/default.json` | Регистрация `animori_page_ready` |
| `src/bridge/IBridge.ts`, `MonkeyBridge.ts`, `TauriProxyDiagnostics.ts` | `markPageReady()` |
| `src/main.ts` | Опрос `#app` (250 мс × 32) и отметка, вне `bootstrap()` |

Коммиты: `e18bc6e`, `02b33a0`, `4b0e8f5`, `84108d0`, `36b2ac9`, `b2df266`, `40254e1`.

### Решения

- Срок 12 с: через мёртвый прокси страница не придёт никогда, живой канал успевает.
- Отсчёт от создания окна, а не от завершения навигации: второе событие в целевом
  случае не наступает.
- Опрос корня, а не отметка на верхнем уровне: бандл выполняется и на странице
  ошибки WebView2.
- Гасится только `set_proxy_on`; адрес, порт и логин сохраняются.
- `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` сносится в начале `apply_to_webview()`,
  до разбора настроек: место лечит любой самостоятельный перезапуск, не только
  аварийный.

### Ошибки итерации

1. Перезапись `proxy.rs` через API оборвала файл на середине (`e5e109a`).
   Восстановлено через `git checkout 84108d0 -- src-tauri/src/proxy.rs`.
   Вывод: файлы ближе 25 КБ правятся только локально, патчем.
   Уточнено позже на `translator/index.ts` — см. «Запись через API» ниже.
2. Четыре записи в одну ветку параллельно — 409. Только последовательно.
3. Команда в `generate_handler!` без префикса модуля — E0425 плюс ложная жалоба
   на never type fallback. Вторая ушла вместе с первой.
4. Прокси переживал перезапуск: `app.restart()` отдаёт потомку окружение
   родителя, поэтому старый `--proxy-server` оставался в силе, хотя в настройках
   уже стояло `set_proxy_on: false`. Выглядело как повторный кирпич после нажатия
   «Выключить и перезапустить». Лечится сносом переменной (`40254e1`).
5. `prettier` переформатировал `README.md` и `CHANGELOG.md` (`b2df266`). Правки
   безобидные (выравнивание таблиц), откачены; оба файла в `.prettierignore`
   (`a8f1451`).

### Проверка

Сборка зелёная. Юзерскрипт 660,89 КБ (gzip 156,59), десктоп 613,52 КБ (gzip 147,77),
CSS 46,76 КБ.

Живая проверка пройдена без настоящего прокси, на двух подделках:

| Случай | Как поднят | Результат |
| --- | --- | --- |
| Отметка доходит | Прокси выключен | В консоли нет жалобы `markPageReady`, диалога нет |
| Порт закрыт | `127.0.0.1:9` | Исход `Unreachable`, трафик напрямую, сторож не заводится |
| Принимает, но не выпускает | `TcpListener` на 8080 из PowerShell, соединения не обслуживаются | Диалог через 12 с; «Оставить как есть» ничего не меняет; «Выключить и перезапустить» гасит тумблер и поднимает живую страницу |
| Живой прокси | Скрипт Node с туннелем `CONNECT` на 8080 | «Ответил за 0 мс, запрос прошёл», страница грузится, диалога нет |

Последняя строка — защита от ложных срабатываний: без неё сторож мог бы
срабатывать всегда.

## Задача: чистка комментариев (вне очереди)

Правило — `docs/CODE-STYLE.md`. Комментарии занимают около 40% веса исходников
и упирают файлы в порог перезаписи. Чистка охватывает весь проект, по 1–3 файла
за итерацию, с замером веса до/после и сборкой после каждой.

Условия: чистка НЕ трогает код, только комментарии. `README.md` и бейджи не
трогаем. Ценное «почему» переезжает в `docs/`, а не удаляется.

### Редакция правила

После чистки `lib.rs` правило ужесточено (`dc20194`): док-комментарий — 2 строки
вместо 3, запрет комментариев из двух абзацев, пустая строка `//` внутри
комментария запрещена. Повод — `NET_PROBE_SCRIPT`, вышедший на 11 строк через
четыре формально коротких абзаца.

Файлы, почищенные до `dc20194`, второй раз не перебираем: они попадут под новые
лимиты при ближайшей содержательной правке.

### Партия 6: `translator/index.ts`

Самый тяжёлый файл очереди: 47 065 → 34 677 б (−12 388 б, −26%). Код не тронут.

Что снято:

- Шапка на 46 строк: пересказ конвейера по шагам, список отличий от монолита,
  два блока «ВАЖНО», разбор пункта 3.8 и ссылка на РИСК №4 — теперь 2 строки.
- Док-комментарии дефектов A6, A7, A8, A11, A12 — по 6–10 строк с историей
  и ссылками на журнал ч.3 §6.9–6.11, местами длиннее самого кода.
- Ссылки на номера строк монолита (2502–3060, 3016, 3021) и на коммит `1306f00`.

Ценное «почему» вынесено в `docs/2.0.1/TRANSLATOR.md` (`3ed1944`, 7293 б): конвейер,
отличия от монолита, маркеры узлов, темп запросов по пункту 3.8 и таблица
разобранных дефектов. Шапка файла ссылается на этот документ.

В коде оставлены короткие «почему», без которых строка читается как ошибка:
маркер ставится после `dbGet`, возврат остатка пачки при 429, приоритет персон,
отсутствие пауз после 3.8, нулевая рамка в `entryDistance`.

Сборка и `typecheck` по этой партии ещё не прогонялись — дописать цифры после
локального прогона.

### Что выяснилось про запись через API

Порог касается текста, который отправляется, а не того, что лежит в репозитории.
Почищенный файл легче исходного, поэтому чистка тяжёлого файла через API
безопасна: `TauriBridge.ts` (25 → 11,6 КБ), `IBridge.ts` (16 → 8,7 КБ) и `main.ts`
(23,5 → 12,6 КБ) записаны без обрывов.

Оценка порога в 25 КБ была заниженной. `translator/index.ts` записан целиком
одним вызовом на 34 677 б, перечитка подтвердила целостность. Значит, обрыв
`proxy.rs` был не чистым эффектом размера. Рабочее правило теперь такое: размер
сам по себе не запрет, но контрольная перечитка после каждой записи
обязательна: обрыв API отдаёт как успех.
