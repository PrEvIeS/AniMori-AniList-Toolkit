## 1. Цель и границы этапа

Цель Этапа 3 — развязать код с функциями менеджера юзерскриптов (`GM_*`) и ввести
абстрактный слой Bridge с двумя реализациями: браузерной и десктопной.
После этапа прикладной код не должен знать, где он работает — в браузере или в оболочке Tauri.

Критерий приёмки: прямых вызовов `GM_*` в `src/` не осталось, юзерскрипт собирается
и ведёт себя так же, как в конце Этапа 2.

Сборка Tauri и нативная оболочка относятся к Этапу 4 (`docs/refactoring/RM4.md`).

### Итерация 3.1 — контракт платформы

Создан `src/bridge/IBridge.ts`: три подсистемы по RM3 — `IStorage`, `IHttp`, `IClipboard` —
и корневой `IBridge` с полем `platform`. Реализаций нет, потребителей пока тоже нет.

Замер подтвердил ожидание: число модулей и размер бандла не изменились ни на байт.
Типы стираются при компиляции, а единственный исполняемый фрагмент — класс `BridgeHttpError` —
выброшен tree-shaking за отсутствием импортов.

Принятые решения по контракту, все — следствие разбора существующего кода:

1. **Хранилище асинхронно всегда**, включая браузер, где ответ готов сразу.
   Равнение по худшему случаю закрывает РИСК №1 сразу: иначе на Этапе 4
   пришлось бы переписывать потребителей второй раз.
2. **Две перегрузки `get`** — с дефолтом и без него. Ровно два способа, которыми код
   пользуется `GM_getValue` сейчас: `core/settings.ts` всегда передаёт дефолт,
   а `getAlToken()` в `api/anilist.ts` читает `AL_TOKEN` без него и проверяет тип вручную.
3. **`http.request` не бросает исключение на код вне 2xx.** Ключевое ограничение,
   продиктованное кодом: `fetchShiki` трактует 404 как «пробуй следующее зеркало»,
   `fetchAnime365ByMal` отличает soft-block 403/502/503/520-524 от «нет данных», а 429 везде
   означает паузу, а не отказ. Преврати статусы в исключения — вся эта логика
   перестанет различать случаи. Отклонение — только транспорт, таймаут, отмена,
   всегда через `BridgeHttpError` с полем `kind`.
4. **Заголовки ответа — объект с ключами в нижнем регистре**, а не сырая строка.
   `anilistQuery` сейчас вытаскивает `retry-after` регуляркой по `responseHeaders`;
   в Tauri заголовки приходят объектом Headers, и без нормализации чтение вело бы себя
   по-разному на разных платформах.
5. **Поле `credentials`** заложено сразу под пункт 3.6 (РИСК №2). Где режим
   `include` честно невыполним — случай Tauri — реализация обязана сходить анонимно
   и записать предупреждение в логгер, а не молча подменять режим.
6. **`GM_addStyle` в контракт не входит.** Прямых вызовов в `src/` нет, единственный
   потребитель — `vite-plugin-monkey`, встраивающий CSS на этапе сборки. Это забота
   сборщика, а не рантайма. Грант в шапке остаётся нетронутым.

Браузерная проверка на этой итерации не проводилась осознанно: поведение скрипта не затронуто.

## 5. Актуальные риски

- **РИСК №1 — синхронное хранилище.** Главный риск этапа. `GM_getValue` синхронен,
  а хранилище Tauri — нет. Весь прикладной код читает настройки через `core/settings.ts`,
  поэтому асинхронным должен стать один модуль, а не все потребители.
  Контракт 3.1 закрепил асинхронность на уровне типов; фактический перевод
  `core/settings.ts` на `await` — пункт 3.5.
- **РИСК №2 — cookies Shikimori недоступны Rust-клиенту.** Упирается в пункт 3.6:
  синхронизация ходит к Shikimori с `window.location.origin` и опирается на сессию браузера.
  В контракте 3.1 под это заведено поле `credentials` с требованием громкого отказа.
- **РИСК №3 — React против Vue.** Закрыт в Этапе 2 через `core/lifecycle.ts` и `vue-mounter`.
- **РИСК №4 — рекурсия мутаций.** Закрыт через `am-notr` и лимиты чисток.
- **Лимиты Shikimori.** 5 запросов в секунду и 90 в минуту на всё приложение.
  Любой новый потребитель обязан ходить через `fetchShiki()` с его ограничителем скорости.
  Шлюз `acquireSlot()` живёт выше транспорта и при переходе на Bridge остаётся на месте:
  мост не должен дать никому его обойти.

## 6. Правила работы

- Файлы отправлять по одному и последовательно: параллельная запись в одну ветку даёт 409.
- Перед локальными коммитами выполнять `git pull --ff-only origin desktop-dev-3`.
- Не использовать динамический `import()`: сборка — однофайловый юзерскрипт.
- Перед перезаписью крупного файла читать его целиком, а не восстанавливать по памяти.
- Разметку и подписи переносить дословно из монолита 1.9.1.
- Селекторы чужой разметки брать только из живого DOM, присланного разработчиком.
- Не удалять узлы, принадлежащие фреймворку чужого сайта: их можно только прятать стилем.
- Не сносить интерфейс на смене роута: `unmountAll()` — только при выгрузке страницы.
- `mount()` медиа-виджета вызывается на каждую пачку мутаций DOM: кэшировать любой исход
  сетевой работы, включая пустой.
- Любая пометка «элемент уже в работе» обязана сниматься при провале обработки,
  а идентификаторы удалять из очереди только после подтверждённого результата.
- `core` не импортирует `features`: связывание подсистем живёт в `main.ts`.
- Собственные данные пользователя на AniList запрашивать с токеном.
- После изменений проверять `npm run typecheck`, `npm run build` и браузерное поведение.
- В конце каждой итерации присылать разработчику команды терминала и пункты сверки.
- Чекбоксы пункта проставлять только после подтверждённой итерации.
- Не запускать `npm audit fix --force`: можно сломать `vite-plugin-monkey`.
- Установка зависимостей и сборка выполняются локально разработчиком.
- Длинные файлы журнала писать прямым текстом: escape-последовательности раздувают запись.
