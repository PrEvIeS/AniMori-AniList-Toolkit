## 1. Цель и границы этапа

Цель Этапа 3 — развязать код с функциями менеджера юзерскриптов (`GM_*`) и ввести
абстрактный слой Bridge с двумя реализациями: браузерной и десктопной.
После этапа прикладной код не должен знать, где он работает — в браузере или в оболочке Tauri.

Критерий приёмки: прямых вызовов `GM_*` в `src/` не осталось, юзерскрипт собирается
и ведёт себя так же, как в конце Этапа 2.

Сборка Tauri и нативная оболочка относятся к Этапу 4 (`docs/refactoring/RM4.md`).

### Итерация 3.1 — контракт платформы

Создан `src/bridge/IBridge.ts`: три подсистемы по RM3 — `IStorage`, `IHttp`, `IClipboard` —
и корневой `IBridge` с полем `platform`. Реализаций нет, потребителей пока тоже нет.

Замер подтвердил ожидание: число модулей и размер бандла не изменились ни на байт.
Типы стираются при компиляции, а единственный исполняемый фрагмент — класс `BridgeHttpError` —
выброшен tree-shaking за отсутствием импортов.

Принятые решения по контракту, все — следствие разбора существующего кода:

1. **Хранилище асинхронно всегда**, включая браузер, где ответ готов сразу.
   Равнение по худшему случаю закрывает РИСК №1 сразу: иначе на Этапе 4
   пришлось бы переписывать потребителей второй раз.
2. **Две перегрузки `get`** — с дефолтом и без него. Ровно два способа, которыми код
   пользуется `GM_getValue` сейчас: `core/settings.ts` всегда передаёт дефолт,
   а `getAlToken()` в `api/anilist.ts` читает `AL_TOKEN` без него и проверяет тип вручную.
3. **`http.request` не бросает исключение на код вне 2xx.** Ключевое ограничение,
   продиктованное кодом: `fetchShiki` трактует 404 как «пробуй следующее зеркало»,
   `fetchAnime365ByMal` отличает soft-block 403/502/503/520-524 от «нет данных», а 429 везде
   означает паузу, а не отказ. Преврати статусы в исключения — вся эта логика
   перестанет различать случаи. Отклонение — только транспорт, таймаут, отмена,
   всегда через `BridgeHttpError` с полем `kind`.
4. **Заголовки ответа — объект с ключами в нижнем регистре**, а не сырая строка.
   `anilistQuery` сейчас вытаскивает `retry-after` регуляркой по `responseHeaders`;
   в Tauri заголовки приходят объектом Headers, и без нормализации чтение вело бы себя
   по-разному на разных платформах.
5. **Поле `credentials`** заложено сразу под пункт 3.6 (РИСК №2).
6. **`GM_addStyle` в контракт не входит.** Прямых вызовов в `src/` нет, единственный
   потребитель — `vite-plugin-monkey`, встраивающий CSS на этапе сборки. Это забота
   сборщика, а не рантайма. Грант в шапке остаётся нетронутым.

Браузерная проверка на этой итерации не проводилась осознанно: поведение скрипта не затронуто.

### Итерация 3.2 — браузерная реализация

Создан `src/bridge/MonkeyBridge.ts`. Это единственное место, где вызовы `GM_*` останутся
после пункта 3.5. Прикладной логики в мосте нет: ограничитель скорости, перебор зеркал,
бэкоффы и повторы остаются выше, в `src/api/`.

Замер снова без изменений: 64 модуля, 591.85 kB. Потребителей у `monkeyBridge` пока нет,
файл целиком выброшен tree-shaking.

Исправление контракта по ходу итерации (коммит `290e9f3`): дефолт `credentials`
изменён с `'omit'` на `'include'`. Первоначальный дефолт был ошибкой: `GM_xmlhttpRequest`
отправляет куки, и все четыре клиента в `src/api/` живут именно так. При дефолте `'omit'`
пункт 3.5 либо потребовал бы проставлять `'include'` в каждый вызов, либо молча изменил
поведение всей сети — прямое нарушение критерия приёмки этапа.

Решения реализации:

1. **`parseRawHeaders()`** разбирает сырую строку `responseHeaders` в объект с ключами
   в нижнем регистре. Повторяющиеся заголовки склеиваются через запятую, как это делает
   штатный `Headers`. Функция экспортирована — пригодится при разборе поведения.
2. **Режим `'omit'` реализован через `anonymous: true`.** Поле поддерживают Tampermonkey
   и Violentmonkey, но не Greasemonkey 4, где оно молча игнорируется и куки всё равно уйдут.
   `supportsAnonymous()` смотрит на `GM_info.scriptHandler` и при неподдержке один раз
   за сессию пишет предупреждение. Контракт запрещает делать вид, что режим сработал.
3. **Предупреждение идёт в `console.warn`, а не в логгер проекта.** Намеренно:
   `utils/logger` читает настройки, а настройки на пункте 3.5 сами пойдут через мост —
   получилась бы циклическая зависимость. Ограничение отмечено комментарием в коде.
4. **`GM_setClipboard` первый, `navigator.clipboard` — фоллбэк.** Порядок из RM3 и он же
   правильный по сути: `GM_setClipboard` синхронен и не требует фокуса документа,
   а `navigator.clipboard` падает на неактивной вкладке и без жеста пользователя.
5. **В `vite-env.d.ts` добавлены `anonymous` и `GM_info`** (коммит `7076494`). Новых грантов
   это не требует: `GM_info` доступен всегда, а `anonymous` — поле уже выданного
   `GM_xmlhttpRequest`. Шапка юзерскрипта не менялась: расширение `@grant` или `@connect`
   привлекает модерацию Greasy Fork.

Проверка в браузере снова не требовалась: код в бандл не попадает.

### Итерация 3.3 — десктопная реализация

Создан `src/bridge/TauriBridge.ts`. В проект добавлены четыре зависимости:
`@tauri-apps/api`, `@tauri-apps/plugin-store`, `@tauri-apps/plugin-clipboard-manager`,
`@tauri-apps/plugin-http`. Они помещены в обычные `dependencies`: на Этапе 4 это рантайм
десктопной сборки. На размер юзерскрипта установка не повлияла: 64 модуля, 591.85 kB.

Оболочка, `Cargo.toml` и разрешения `capabilities` в этот пункт не входят — это Этап 4.
До первой десктопной сборки код файла нигде не исполняется и проверен только типами.

Решения реализации:

1. **`LazyStore` вместо `load()`.** `load()` возвращает промис и потребовал бы либо
   верхнеуровневого `await`, либо ручной инициализации из `main.ts` — то есть разных
   точек входа для двух платформ, чего этап как раз избегает. `LazyStore` создаётся
   синхронно и читает файл при первом обращении. Флаг `autoSave` пишет файл сам после
   `set()` — ближайший аналог поведения `GM_setValue`. Файл хранилища — `animori-settings.json`.
2. **Дефолт подставляется вручную.** `store.get()` второго аргумента не принимает
   и возвращает `undefined` для отсутствующего ключа, в отличие от `GM_getValue`.
   Без ручной подстановки обе перегрузки контракта вели бы себя по-разному
   на разных платформах.
3. **Таймаут через `AbortController`, а не через `connectTimeout` плагина.** `connectTimeout`
   ограничивает только фазу установки соединения, а `GM_xmlhttpRequest` отсчитывает таймаут
   на весь запрос. Именно на это опирается перебор зеркал в `fetchShiki` с его 5000 мс:
   возьми мы `connectTimeout`, зеркала перестали бы переключаться на медленных ответах.
   Флаг `timedOut` отличает собственный таймаут от внешней отмены, чтобы `kind` был честным.
4. **У буфера обмена фоллбэка нет — осознанно.** В браузерной реализации фоллбэк
   оправдан, а здесь падение плагина означает невыданное разрешение
   `clipboard-manager:allow-write-text`, то есть ошибку конфигурации Этапа 4.
   Её надо видеть, а не глушить тихим обходным путём.
5. **`res.headers.forEach` с приведением к нижнему регистру** даёт ровно тот же вид,
   что `parseRawHeaders` собирает вручную в `MonkeyBridge`.

Предупреждения `npm audit` (7 уязвимостей) оставлены без действий: `npm audit fix --force`
ломает `vite-plugin-monkey`. Разбор — на приёмке Этапа 4.

### Итерация 3.4 — выбор реализации на этапе сборки

Создан `src/bridge/index.ts` — единственная точка входа к мосту для прикладного кода.
Он реэкспортирует типы из `IBridge` и сам мост под именем `Bridge`. Затронуты пять файлов:
обе реализации, новая точка входа, `vite.config.ts` и `tsconfig.json`.

Замер прежний: 64 модуля, 591.85 kB. Ожидаемо и на этот раз ничего не доказывает —
потребителей у `index.ts` ещё нет, в граф модулей он не входит. Содержательным критерием
размер станет на 3.5, когда мост начнут импортировать настройки и сетевые клиенты.
Проверку алиаса на этой итерации выполнил `vue-tsc`: при неверном `paths` он упал бы
с `TS2307: Cannot find module '@bridge-impl'`.

Решения реализации:

1. **Подмена пути вместо ветвления в коде.** Схема «импортировать оба моста и выбрать
   по `__ANIMORI_PLATFORM__`» отвергнута: `TauriBridge` создаёт `LazyStore` на верхнем
   уровне модуля, а такой побочный эффект Rollup вправе сохранить даже после удаления
   недостижимой ветки — вместе с ним в юзерскрипт уехали бы пакеты `@tauri-apps/*`.
   `resolve.alias` разрешает псевдопуть `@bridge-impl` в один конкретный файл,
   и вторая реализация в граф модулей не попадает вовсе. Запасной вариант с `external`
   не понадобился.
2. **Общее имя экспорта `platformBridge`** добавлено в обе реализации как алиас
   к существующим `monkeyBridge` и `tauriBridge`. Подмена пути требует, чтобы оба файла
   экспортировали одинаковое имя; старые имена сохранены, сама логика не тронута.
3. **Ключ `@bridge-impl` стоит перед `@` в объекте алиасов.** Совпадение строковых алиасов
   идёт по порядку. Пересечения между ключами всё равно нет — `@` срабатывает только
   на точном совпадении либо на префиксе `@/`, — но порядок зафиксирован явно,
   чтобы вопрос не возникал при следующих правках конфига.
4. **`tsconfig.json` указывает `@bridge-impl` на `MonkeyBridge`.** Тайпчекеру нужна одна
   фиксированная цель, и браузерная реализация взята как основная. На проверку выбор
   не влияет: обе реализации объявлены как `IBridge`, а `TauriBridge` входит в `include`
   и проверяется сам по себе.
5. **Мост экспортируется как `Bridge`** — имя из RM3, под которым его ждут пункты 3.5 и 3.6.

Отдельно зафиксировано правило для прикладного кода: импортировать разрешено только
`@/bridge`. Прямой импорт `TauriBridge` из любого места вне `src/bridge` немедленно вернёт
пакеты Tauri в бандл юзерскрипта в обход алиаса.

Перед этой итерацией в ветку доехал коммит `6c8627b` с `package.json` и `package-lock.json`
после установки пакетов Tauri: файлы генерируются npm локально и восстановлению по памяти
не подлежат.

### Итерация 3.5.1 — настройки на асинхронном хранилище

Первая итерация пункта 3.5 и первая за этап, где меняется поведение работающего кода.
Затронуты два файла: `src/core/settings.ts` (коммит `f80bfb7`) и `src/utils/logger.ts`
(коммит `327bd25`).

Замер впервые показал движение: **67 модулей, 597.38 kB, gzip 140.61 kB** против 64 и 591.85 kB.
Прибавка ровно та, которую и следовало ожидать: три модуля — `bridge/index.ts`, `IBridge.ts`
и `MonkeyBridge.ts` — вошли в граф, потому что у моста появился первый потребитель.
Плюс 5.53 kB при выключенной минификации — это код `MonkeyBridge` вместе с его комментариями.
Следов `@tauri-apps/*` нет: любой из четырёх пакетов дал бы прибавку на порядок больше
и десятки модулей. Механизм подмены пути из 3.4 работает.

Решения реализации:

1. **Дефолты вынесены в константу `DEFAULT_SETTINGS`.** Раньше значения по умолчанию жили
   вторыми аргументами двадцати с лишним вызовов `GM_getValue`, а сам объект `settings`
   получался синхронным вызовом `readSettings()` прямо на импорте модуля. С асинхронным
   хранилищем так больше нельзя, и дефолты понадобились дважды: как стартовое состояние
   `settings` до конца загрузки и как значения по умолчанию самого чтения.
2. **Все ключи читаются одним `Promise.all`.** В браузере разницы нет — `GM_getValue`
   отвечает мгновенно, — но в Tauri последовательный `await` превратился бы в двадцать два
   последовательных обращения через IPC на старте приложения.
3. **Legacy-фоллбэк `set_titles` сохранён, но переписан.** Раньше старый ключ стоял вторым
   аргументом вложенного `GM_getValue` и читался лениво. Теперь оба ключа читаются
   параллельно, а старый применяется только при отсутствии нового. Поведение то же,
   цена — одно лишнее чтение из хранилища.
4. **`saveSetting()` обновляет память ДО записи в хранилище.** Интерфейс обязан
   отреагировать на клик мгновенно, как было с синхронным `GM_setValue`. Сбой записи
   не откатывает значение: пользователь дорабатывает сессию в выбранном режиме,
   и теряется только сохранение выбора между перезагрузками.
5. **`saveSetting()` асинхронна, но не отклоняется.** Её зовут из setter'ов реактивных
   моделей в `settings-state.ts`, где дождаться результата физически негде.
   Отклоняйся она — каждый сбой записи всплывал бы глобальным `unhandledrejection`,
   который логгер к тому же принял бы за нашу ошибку. Поэтому ошибка ловится внутри
   и уходит в `console.error`.
6. **Диагностика через `console`, а не через `Logger`.** `utils/logger` импортирует
   настройки; обратный импорт замкнул бы цикл. То же ограничение, что и внутри моста.

Отдельная находка по ходу итерации — **`utils/logger.ts`**. Он восстанавливал логи сессии
из `sessionStorage` на верхнем уровне модуля, проверяя `settings.enableLogger`. Импорты
выполняются до `bootstrap()`, то есть после перехода на асинхронное чтение там всегда
оказался бы дефолт `true`, и логи восстанавливались бы даже при выключенном логгере.
Восстановление переехало в `installGlobalErrorHandlers()`, который `bootstrap()` вызывает
сразу после `await loadSettings()`: оба действия зависят от одного флага и оба требуют
уже загруженных настроек. Сам `sessionStorage` через мост сознательно не пошёл — это память
вкладки, а не настройки приложения, и в WebView Tauri она работает штатно.

`settings-state.ts` в этой итерации не тронут намеренно. Setter'ы зовут `saveSetting()`
без `await`, но промис не отклоняется, так что потерять ошибку невозможно. Прямые
`GM_getValue('AL_TOKEN')` и `GM_setClipboard` в нём остаются и уйдут вместе с остальными
остатками, чтобы не переписывать файл дважды.

Проверка в браузере: панель настроек открывается, положения переключателей сохранены,
смена тумблеров, акцента и источника тайтлов переживает перезагрузку, логгер ведёт себя
по своему флагу. Аномалий не выявлено.

### Итерация 3.5.2 — сетевой слой на `Bridge.http`

Весь `src/api/` переведён с коллбэков `GM_xmlhttpRequest` на `async/await` поверх
`Bridge.http`. Пять файлов, пять коммитов, каждый проверен разработчиком отдельной сборкой:
`animethemes.ts` (`1df2499`), `anime365.ts` (`7c2f213`), `anilist.ts` (`5532a9a`),
`shikimori.ts` (`7f58a01`), `shikimori-people.ts` (`2c3b69c`).

Замер: **67 модулей, 596.40 kB, gzip 140.64 kB** — против 67 и 597.38 kB после 3.5.1.
Бандл не вырос, а похудел примерно на килобайт. Это ожидаемо: новых модулей в граф
не добавилось (мост вошёл туда ещё на 3.5.1), а обвязки `new Promise` с четырьмя
коллбэками в каждом клиенте исчезли. Прибавка комментариев съела часть выигрыша,
отсюда колебания в пределах полукилобайта между промежуточными замерами.
Пакетов `@tauri-apps/*` в сборке по-прежнему нет.

**Пятый файл в плане не значился.** Пункт 3.5.2 описывал четыре клиента, но
`api/shikimori-people.ts` вёл собственную обвязку над `GM_xmlhttpRequest`, отдельную
от `fetchShiki`. Без него критерий приёмки этапа не выполнялся бы, а в десктопной сборке
молча отвалился бы поиск персонажей и авторов. Находка — прямое следствие правила
«перед правкой модуля читать его потребителей и соседей».

Общий шаблон перевода, одинаковый для всех пяти файлов:

1. **Импорт только `@/bridge`.** Тип `HttpResponse` импортируется лишь там, где нужно
   объявление `let res:` до присваивания. `BridgeHttpError` не импортируется нигде:
   неиспользованный импорт роняет `vue-tsc`, а различать `kind` ни одному клиенту
   пока не требуется — все три вида транспортного сбоя обрабатываются одинаково.
2. **Каждый статус разбирается явной веткой.** Мост по контракту не бросает исключение
   на код вне 2xx, поэтому 429, 404, soft-block и «всё остальное» стали обычными `if`
   вместо разбора внутри `onload`. Порядок веток сохраняет прежние приоритеты.
3. **`try/catch` только вокруг самого запроса.** Внутрь него попадают транспорт, таймаут
   и отмена — ровно то, что мост отклоняет.
4. **Все строки `Logger` перенесены дословно.** Диагностика в панели логов — единственный
   способ разбирать жалобы пользователей, и её текст не должен разъезжаться с монолитом.
5. **Прикладная логика в мост не переехала.** Ограничитель скорости Shikimori,
   перебор зеркал, бэкоффы `anime365`, разбор `retry-after` и кэши остались на месте.

Найдено и исправлено по ходу — **три одинаковых висяка**. В `anime365.ts`, `anilist.ts`
и `shikimori.ts` разбор ответа `JSON.parse` стоял внутри коллбэка `onload`. Исключение
оттуда никуда не всплывало: обёртывающий промис оставался неразрешённым навсегда,
и вызывающий код ждал вечно. Для пользователя это выглядело как бесконечная загрузка
виджета без единой ошибки в журнале. После перевода это обычное пойманное исключение:
запрос считается неудачным, `shikimori.ts` уходит на следующее зеркало, остальные
отдают штатный отказ. Случай воспроизводился только на битом ответе сервера,
поэтому за всё время в жалобах не всплывал.

Частные решения по файлам:

- **`animethemes.ts`.** Сохранён контракт «никогда не отклоняется»: любой сбой — `null`.
  Кэш `THEMES2_<malId>` в `shikiCache` кэширует в том числе пустой результат — без этого
  `mount()` медиа-виджета бил бы в сеть на каждую пачку мутаций DOM. Разбор ответа вынесен
  в отдельную `formatThemes()`, повтор на 429 остался через 1500 мс с джиттером.
- **`anime365.ts`.** Введены `BLOCKED_STATUSES` (403, 502, 503, 520–524) и общая
  `registerFailure()`, куда сведены отключение источника на сессию и пауза 15 секунд.
  Раньше эта пара повторялась в трёх местах и уже расходилась между ними.
  Пауза `ANIME365_THROTTLE` после каждого ответа сохранена.
- **`anilist.ts`.** Разбор `retry-after` переехал с регулярки по сырой строке заголовков
  на чтение `headers['retry-after']` — ровно ради этого в контракте 3.1 заголовки
  нормализованы в объект. Регулярка на Tauri молча не срабатывала бы, и вместо честной
  паузы клиент долбил бы AniList до бана. `getAlToken()` оставлен на `GM_getValue`
  осознанно: он часть пункта 3.5.3 вместе с остальными ключами.
- **`shikimori.ts`.** Шлюз `acquireSlot()` (300 мс между запросами, 60 в минуту скользящим
  окном) не тронут ни строкой. Сохранена и тонкость перебора зеркал: 404 не финальный ответ,
  а повод идти на следующий домен — тайтл могли снять по требованию РКН на основном зеркале,
  но он жив на `.rip`. «Не найдено» запоминается и отдаётся, только если так ответили все.
- **`shikimori-people.ts`.** Изменена ровно одна функция — локальная обёртка `request()`.
  Стратегия поиска (три REST-варианта, фоллбэк на GraphQL, дозагрузка деталей), порог
  совпадения, гард тёзок по общим MAL id и кэш ролей остались нетронутыми. Обёртка
  по-прежнему не отклоняется и отдаёт `status: 0` на транспортном сбое: одно упавшее
  зеркало не должно ронять перевод всей страницы.

Ложная тревога по ходу итерации: после перевода `anime365.ts` разработчик сообщил,
что не тянутся названия и описания манги. Причина не в коде — в моих же пунктах сверки
было сказано выставить anime365 основным источником тайтлов, а у anime365 манги нет вовсе
(`if (!malId || type === 'MANGA') return null` — так с монолита). Мангу отдаёт только
ветка Shikimori в `api/titles.ts`. Правило на будущее внесено в раздел 6.

Проверка в браузере: русские названия и описания аниме и манги, рейтинги, франшиза,
темы OP/ED, персонажи и авторы, сканер и очередь перевода. Аномалий не выявлено
ни на одном из пяти шагов.

### Итерация 3.5.3 — остатки `GM_*` и сплошная проверка `src/`

Заключительная итерация пункта 3.5. Разбита на четыре подхода, каждый проверен
разработчиком отдельной сборкой: **а** — свои ссылки и пользовательский словарь (`1b9b2bd`),
**б** — токен AniList, буфер обмена и состояние синхронизации (`0d36218`),
**в** — сканер сравнения и музыкальные темы (`4d64c1a`),
**г** — сплошная проверка всего `src/` и две находки (`b14f7d5`).

Итоговый замер: **67 модулей, 599.59 kB, gzip 141.25 kB**. Рост от 596.40 kB после 3.5.2
объясняется целиком: в каждом переведённом модуле появился кэш в памяти, функция загрузки
и обработчик ошибок вместо одной строки `GM_getValue`. Числа модулей не изменилось —
новых файлов не добавлялось, а пакетов `@tauri-apps/*` в сборке по-прежнему нет.

**Общий приём итерации — кэш в памяти перед синхронным чтением.** Хранилище стало
асинхронным, а места чтения остались синхронными: `mount()` медиа-виджета, обработчик
клика по сердечку, сборка списка ссылок. Переписывать их все на `await` означало бы
тянуть асинхронность в отрисовку и получить моргание интерфейса. Вместо этого в каждом
модуле заведён кэш: данные читаются один раз перед показом (`loadCustomLinks()`,
`loadUserDict()`, `loadAlToken()`, `loadScannerStorage()`, `loadService()`,
`loadFavTranslations()`), дальше синхронные функции работают с памятью, а запись идёт
«сначала в память, потом в хранилище» — интерфейс отвечает мгновенно, как раньше.
Сбой записи не откатывает значение и уходит предупреждением в журнал.

Что переведено по подходам:

- **а.** `core/custom-links.ts` (`am_custom_links`) и `core/dictionary.ts` (`am_user_dict`).
  В `main.ts` добавлена загрузка обоих ключей одним `Promise.all` до запуска переводчика:
  иначе первая волна перевода прошла бы по пустому пользовательскому словарю, и правки
  пользователя применились бы только после первой смены страницы.
- **б.** `api/anilist.ts` (`AL_TOKEN` через `loadAlToken`/`getStoredAlToken`/`setAlToken`),
  `utils/dom.ts` (копирование в буфер обмена через `Bridge.clipboard`),
  `features/ui/settings-state.ts` и `features/exporter/sync-state.ts`.
  Загрузка токена встала в `main.ts` до ветки Shikimori: экспортёр запускается именно там,
  и без токена в памяти он открывался бы с пустым полем при сохранённом токене.
- **в.** `features/scanner/compare.ts` (`CMP_IGNORE`, `SHIKI_LOGIN`) вместе с
  `scanner-state.ts` и `features/media/themes.ts` (`am_music_service`).
  Сканер грузит игнор-лист и логин **до** показа окна: иначе окно открывалось бы с пустым
  полем логина, а скрытые ранее строки на секунду возвращались бы в результаты.
  Битый игнор-лист теперь сбрасывается в пустой с предупреждением, а не роняет сканер.

**Подход «г» — сплошная проверка.** После трёх подходов список из плана был исчерпан,
но на 3.5.2 уже выяснилось, что план неполон. Поэтому прочитаны все файлы `src/` подряд.
Найдено ещё два места, ни одного из них в плане не было:

1. **`api/dictionary.ts`** качал общий словарь интерфейса через `GM_xmlhttpRequest`.
   В десктопной сборке словарь не загрузился бы вообще, и интерфейс остался бы английским
   при включённом переводе. Функция переведена на `Bridge.http`, контракт «никогда
   не отклоняется» сохранён, добавлена запись в журнал при неудачной загрузке —
   раньше отказ был полностью молчаливым.
2. **`features/media/player.ts`** — два места сразу: запрос к базе Kodik
   (`GM_xmlhttpRequest`) и список любимых озвучек `am_fav_translations`
   (`GM_getValue`/`GM_setValue`). Без первого на десктопе плеер всегда сваливался бы
   в резервный вариант — без выбора озвучки и без сетки серий. Второе давало заметный
   эффект уже сейчас: список любимых читался не вовремя, и плеер стартовал на первой
   попавшейся озвучке вместо отмеченной сердечком. Теперь список читается вместе
   с данными плеера, до отрисовки.

Заодно в `player.ts` устранён **четвёртый висяк того же вида**, что три найденных на 3.5.2:
`JSON.parse` ответа Kodik стоял внутри коллбэка `onload`, и битый ответ оставлял окно
плеера в состоянии «Подключение к базе...» навсегда. Теперь это обычный пойманный сбой
с переходом на резервный плеер.

Остальные файлы проверку прошли чисто: адблок, поиск, захват выделения, переводчик
и его правила, кэш IndexedDB, логгер и его окно, панель действий, роутер SPA, монтировщик
Vue, рейтинги, франшиза, каркас медиа-страницы, внешние ссылки, экспортёр и все
Vue-компоненты. Отдельно отмечено, что `utils/logger.ts` и `logger-state.ts` продолжают
работать с `sessionStorage` напрямую — это память вкладки, а не настройки приложения,
и в WebView Tauri она работает штатно. Так же осознанно оставлен обычный `fetch`
в `features/exporter/sync-api.ts`: это РИСК №2, он решается на 3.6.

Проверка в браузере по итогам итерации: свои ссылки и пользовательский словарь
сохраняются и применяются сразу, токен AniList подхватывается после перезагрузки,
копирование в буфер работает, сканер открывается с сохранённым логином и игнор-листом,
выбор музыкального сервиса переживает перезагрузку, плеер открывается со списком озвучек
и серий, сердечко сохраняется, перевод интерфейса на месте. Аномалий не выявлено.

**Пункт 3.5 закрыт: в `src/` не осталось ни одного вызова `GM_*` вне `MonkeyBridge.ts`.**

## 5. Актуальные риски

- **РИСК №1 — синхронное хранилище. Закрыт.** Итерация 3.5.1 перевела настройки,
  итерация 3.5.3 — все остальные ключи: `AL_TOKEN`, `am_custom_links`, `am_user_dict`,
  `CMP_IGNORE`, `SHIKI_LOGIN`, `am_music_service`, `am_fav_translations`. Везде применена
  одна схема: загрузка в кэш до первой отрисовки, синхронное чтение из памяти, запись
  «сначала память, потом хранилище». Остаточное наблюдение: любой новый ключ обязан
  заводиться по той же схеме, иначе интерфейс снова начнёт открываться с пустыми полями.
- **РИСК №2 — cookies Shikimori недоступны Rust-клиенту.** Упирается в пункт 3.6:
  синхронизация ходит к Shikimori с `window.location.origin` и опирается на сессию браузера.
  В контракте 3.1 под это заведено поле `credentials` с требованием громкого отказа.
  Реализация 3.3 пробрасывает `credentials` в fetch плагина, но Rust-клиент ведёт собственное
  хранилище куки и к сессии браузера пользователя доступа не имеет. Окончательное решение
  вырабатывается на 3.6 совместно с пунктом 2.7 RM4 об открытом профиле.
- **РИСК №3 — React против Vue.** Закрыт в Этапе 2 через `core/lifecycle.ts` и `vue-mounter`.
- **РИСК №4 — рекурсия мутаций.** Закрыт через `am-notr` и лимиты чисток.
- **Попадание пакетов Tauri в бандл юзерскрипта.** Введён пунктом 3.3, механизм защиты
  построен на 3.4 и впервые проверен на деле в 3.5.1: у моста появился потребитель,
  в граф вошли ровно три браузерных модуля, прибавка 5.53 kB. После 3.5.2 и 3.5.3 число
  модулей не изменилось — пакетов Tauri в сборке нет.
  Риск понижен до наблюдения: замер размера остаётся обязательным на каждой итерации,
  а прямой импорт `TauriBridge` вне `src/bridge` по-прежнему обходит защиту.
- **Лимиты Shikimori.** 5 запросов в секунду и 90 в минуту на всё приложение.
  Любой новый потребитель обязан ходить через `fetchShiki()` с его ограничителем скорости.
  Шлюз `acquireSlot()` живёт выше транспорта и при переходе на Bridge остался на месте:
  мост не должен дать никому его обойти.

## 6. Правила работы

- Файлы отправлять по одному и последовательно: параллельная запись в одну ветку даёт 409.
- Перед локальными коммитами выполнять `git pull --ff-only origin desktop-dev-3`.
- Незакоммиченные правки коммитить до любых переключений и сбросов веток: рабочее дерево
  общее для всех веток, и `git reset --hard` сносит его вместе с историей.
- Не использовать динамический `import()`: сборка — однофайловый юзерскрипт.
- Прикладной код импортирует мост только как `@/bridge`: прямой импорт `TauriBridge`
  возвращает пакеты Tauri в бандл юзерскрипта в обход алиаса сборки.
- Не импортировать `BridgeHttpError` ради красоты: неиспользованный импорт роняет `vue-tsc`.
- При переводе клиента на мост каждый код ответа разбирать явной веткой: мост не бросает
  исключение на статусы вне 2xx, и «упавший» запрос молча пройдёт как успешный.
- Список мест для правки из плана считать неполным: перед закрытием пункта проходить
  весь `src/` файл за файлом. На 3.5.2 так нашёлся пятый сетевой клиент, на 3.5.3 —
  словарь интерфейса и плеер, которых в плане не было вовсе.
- Синхронное чтение из хранилища заменять кэшем в памяти: загрузка до первой отрисовки,
  запись сначала в память, потом в хранилище. Иначе окна открываются с пустыми полями,
  а виджеты стартуют на значениях по умолчанию.
- Настройки читать только в момент использования, `settings.x`. Чтение на верхнем уровне
  модуля даёт дефолт: импорты выполняются до `bootstrap()` и до `await loadSettings()`.
- Копировать значения настроек в собственные константы модуля запрещено по той же причине.
- Разбор ответа (`JSON.parse`) держать там, где исключение будет поймано. В коллбэке
  промиса он оставляет вызывающий код висеть навсегда без единой записи в журнале.
- Перед перезаписью крупного файла читать его целиком, а не восстанавливать по памяти.
- Перед правкой модуля читать также его потребителей: контракт, написанный без оглядки
  на вызывающий код, приходится править следующей же итерацией (случай `credentials`).
- Пункты сверки, требующие изменить настройки, обязаны содержать шаг возврата настроек
  обратно: иначе следующая же проверка даст ложную тревогу (случай манги и anime365).
- Сигнатуры внешних библиотек сверять с документацией перед написанием кода, а не по памяти.
- Зависимости ставятся ПЕРЕД отправкой кода, который их импортирует, иначе падает `vue-tsc`.
- `package.json` и `package-lock.json` коммитит разработчик локально: lock генерируется npm
  под конкретное дерево зависимостей и восстановлению по памяти не подлежит.
- Разметку и подписи переносить дословно из монолита 1.9.1.
- Селекторы чужой разметки брать только из живого DOM, присланного разработчиком.
- Не удалять узлы, принадлежащие фреймворку чужого сайта: их можно только прятать стилем.
- Не сносить интерфейс на смене роута: `unmountAll()` — только при выгрузке страницы.
- `mount()` медиа-виджета вызывается на каждую пачку мутаций DOM: кэшировать любой исход
  сетевой работы, включая пустой.
- Любая пометка «элемент уже в работе» обязана сниматься при провале обработки,
  а идентификаторы удалять из очереди только после подтверждённого результата.
- `core` не импортирует `features`: связывание подсистем живёт в `main.ts`.
- `bridge` не импортирует ни `core`, ни `utils`: логгер и настройки сами пойдут через мост,
  и любой такой импорт даст цикл. Диагностика внутри моста — только `console`.
- Функции, которые зовут из setter'ов реактивных моделей, не должны отклоняться:
  дождаться их там негде, а непойманный reject всплывёт глобальным `unhandledrejection`.
- Собственные данные пользователя на AniList запрашивать с токеном.
- После изменений проверять `npm run typecheck`, `npm run build` и браузерное поведение.
- В конце каждой итерации присылать разработчику команды терминала и пункты сверки.
- Чекбоксы пункта проставлять только после подтверждённой итерации.
- Не запускать `npm audit fix --force`: можно сломать `vite-plugin-monkey`.
- Шапку юзерскрипта не расширять: новые `@grant` или `@connect` привлекают модерацию
  Greasy Fork.
- Установка зависимостей и сборка выполняются локально разработчиком.
- Длинные файлы журнала писать прямым текстом: escape-последовательности раздувают запись
  и приводят к обрыву содержимого на середине.
