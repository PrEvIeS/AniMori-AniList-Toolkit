## Назначение

Цель Этапа 2 — полный отказ от генерации интерфейса строками и ручного управления
DOM в пользу компонентов Vue 3 (Composition API). Никакого Bridge и Tauri на этом этапе
нет — это Этапы 3 и 4. Бизнес-логика ядра не переписывается: меняется только слой
представления.

Критерий приёмки: императивные модули `features/ui/` удалены, поведение интерфейса
совпадает с версией 2.0.0 из `desktop-dev-1`, а сборка юзерскрипта остаётся единственным
таргетом.

Правила ведения журнала перенесены из Этапа 1: пишем решения и причины, а не пересказ
диффа; обновляется по завершённым итерациям, а не по коммитам; держим компактным,
потому что у API нет операции «дописать в файл» и любая правка — передача всего файла.

История Этапа 1 в эту ветку не переносится. Она осталась в `desktop-dev-1`
(`docs/DEVELOPMENT_LOG.md` и поблочный архив `docs/DEVELOPMENT_LOG_BIG.md`).

## 2. Порядок работ и отклонения от RM2

Планируемый порядок: 2.1 → 2.5 → 2.3 → 2.2 → 2.4 → 2.7 и 2.8 → 2.9.

Причины отклонения от нумерации RM2:

1. **Логгер (2.3) идёт раньше настроек (2.2).** Он втрое меньше и уже развязан с ядром
   через `registerLogSink()`, поэтому на нём дешевле обкатать `vue-mounter` и реестр
   приложений, чем на 40 КБ настроек.
2. **Реестр смонтированных приложений делается в 2.1, а не в 2.9.** РИСК №3 (React сносит
   чужие узлы) актуален с момента первого `mount()`, а не с конца этапа. В 2.9 остаётся
   только SPA-часть: реакция на смену роута и массовый `unmount()`.
3. **Медиа-виджеты на этом этапе не переводятся на Vue.** В RM2 они не упомянуты, и это
   верно: модалки в `document.body` безопасны, а инъекция внутрь React-дерева сайдбара —
   нет. Сначала закрывается безопасный контур.

## 3. Риски, актуальные именно для этого этапа

Из `AUDITION.md`, с привязкой к точкам кода:

- **РИСК №3 — React против Vue.** Модалки в `document.body` вне опасности, но любой
  смонтированный корень всё равно регистрируется в реестре: если контейнер исчез из DOM,
  нужны `app.unmount()` и пересоздание, иначе получаем zombie-компоненты и утечки.
  Готовые точки восстановления из Этапа 1: `ensureMediaWidgets()` в `features/media/index.ts`
  и наблюдатель выпадашки в `features/search/index.ts`.
- **РИСК №4 — рекурсия мутаций.** Vue генерирует сотни микро-мутаций на каждом
  реактивном обновлении. `vue-mounter` обязан вешать `am-notr` на корневой узел
  **до** вызова `mount()`, иначе наблюдатель переводчика успеет зайти в свежую разметку.
  Отдельно учесть квирк Этапа 1: оверлей логгера `am-notr` не помечен, как и в 1.9.1;
  при переводе на Vue это перестаёт быть безобидным и должно быть исправлено.
- **РИСК №6 — память логгера.** До 1000 записей на тип без виртуализации — до шести
  тысяч узлов в DOM. Закрывается вместе с `LoggerModal.vue` (п. 2.3): кольцевой буфер
  300-500 записей или виртуальный список.
- **РИСК №1 — асинхронное хранилище.** На этом этапе не блокер, но `watch(settings, ...)`
  из п. 2.2 обязан писать через `core/settings.ts`, а не звать `GM_setValue` из компонента.

РИСКИ №2 и №5 к этапу не относятся: они про сеть и кодеки в Tauri.

### Итерация 1 — пункт 2.1: среда и стратегия монтирования

Файлы: `package.json`, `vite.config.ts`, `tsconfig.json`, новый `src/utils/vue-mounter.ts`.
Коммиты: `5329436` (зависимости), `20c09d3` (конфиг Vite), `db7dc16` (типопроверка),
`665d53c` (монтирование). Отправлялись по одному, последовательно — правило этапа 1
соблюдено, HTTP 409 не было.

Принятые решения и причины:

1. **`vue` — в `dependencies`, не в `devDependencies`.** Рантаим уезжает в бандл юзерскрипта,
   а не остаётся инструментом сборки. В девах только `@vitejs/plugin-vue` и `vue-tsc`.
2. **`vue()` в плагинах строго до `monkey()`.** Плагин юзерскрипта пакует итоговый код
   и не умеет в SFC — ему должен прийти уже скомпилированный JS.
3. **`typecheck` и `build` переведены на `vue-tsc`.** Чистый `tsc` молча игнорирует `.vue`,
   и ошибки шаблонов вылезали бы только в рантаиме. Заодно `src/**/*.vue` в `include`
   и `jsx: preserve` — без них компоненты вне области проверки.
4. **`__VUE_OPTIONS_API__: false`, devtools и hydration-details выключены.** Options API нигде
   не используется, только Composition API. Без этих `define` рантаим сыплет
   предупреждения в консоль пользователя и тащит лишний код.
5. **`am-notr` вешается до вставки корня в документ, а не после.** Порядок
   в `mountApp`: создать узел → повесить классы → `appendChild` → `mount()`. Любая другая
   последовательность оставляет окно, в котором наблюдатель переводчика уже видит узел,
   но иммунитета на нём ещё нет (РИСК №4).
6. **Наблюдение за пропажей корня — без `subtree`, только `childList` родителя.**
   Подписка на поддерево ловила бы собственные рендеры Vue и вернула ту же рекурсию,
   от которой ушли. Включается только флагом `watchContainer`: для модалок в `body`
   наблюдение — пустая трата, оно нужно только для инъекций в React-дерево.
7. **Повторный `mountApp` с тем же ключом не плодит второе приложение.** Модалки
   открываются из разных мест (панель, горячие клавиши, ссылки), и без этой проверки
   мы бы получили два экземпляра одной панели настроек. Если зарегистрированный корень
   отвалился от документа (`isConnected === false`), старое снимается и монтируется заново.
8. **`app.config.errorHandler` на каждом приложении.** Сбой в одном компоненте уходит
   в `Logger`, а не роняет переводчик и поиск. Логика та же, что у `safeCall` из этапа 1.
9. **`getExposed()` вместо глобальных флагов видимости.** Панель действий из п. 2.5
   будет открывать модалки через `defineExpose({ isVisible })`, не зная о их внутренностях.
10. **`vue-mounter` не знает о `GM_*`.** Ни хранилища, ни сети в модуле нет сознательно —
    на этапе 3 он переезжает в Tauri без правок.

Что получил остальной код: `mountApp`, `unmountApp`, `unmountAll`, `getApp`, `getRoot`,
`getExposed`, `listMountedApps`, класс корня `am-vue-root` и id вида `am-vue-<ключ>`.
`listMountedApps()` сразу закладывается в дамп состояния логгера (п. 2.3): без списка
живых корней отлаживать фантомные компоненты нечем.

Не сделано в этой итерации и почему:

- **Сборка и типопроверка не запущены.** Установка зависимостей и `npm run build`
  возможны только локально. До проверки разработчиком пункт 2.1 считается незакрытым,
  а размер бандла в таблице — неизвестным. Ожидаемый прирост от рантайма Vue —
  порядка 50-60 kB до минификации, и это ожидаемо, а не регрессия.
- **Ни одного `.vue` ещё нет.** Первый компонент сознательно будет боевым
  (`ActionPanel.vue`), а не выбрасываемой заглушкой: заглушка проверит то же самое,
  но потребует отдельного коммита на удаление.
- **`main.ts` не тронут.** Пока нет компонентов, менять порядок `bootstrap()` незачем;
  это работа пункта 2.6.

## 6. Правила работы, перенесённые из этапа 1

Грабли, которые уже стоили времени и не должны повториться:

- **Абсолютные адреса — только конкатенацией.** Литерал схемы внутри шаблонной строки
  сворачивается при передаче файла в репозиторий. Это первопричина всей серии битых
  ссылок этапа 1. После отправки файлы с URL перечитывать с ветки.
- **Файлы отправляются по одному, последовательно.** Параллельная отправка даёт гонку
  по ref и HTTP 409; ветка остаётся несобираемой.
- **После пакетного пуша проверять содержимое каталога.** На этапе 1 два пуша довезли
  только часть файлов без ошибки, и `main.ts` ссылался на несуществующий модуль.
- **Поиск по коду в API не индексирует эти ветки** — работают только чтение конкретных
  файлов и grep по локальной копии.
- **Журнал отправляется только литеральным UTF-8** и держится компактным: файл на 51 КБ
  на этапе 1 рвался при отправке. При росте — разбивать по блокам, а не наращивать.
- **Нет удаления веток через интеграцию.** Создание есть, удаление и переименование —
  вручную на стороне разработчика.
- **Пуш идёт прямо в `desktop-dev-2`** без feature-веток и PR; сборка проверяется локально
  после каждой итерации. Откат — сравнение с `desktop-dev-1`.
