# Правила ведения документации

Этот файл главнее привычек. Если документ не описан здесь — его не заводим.

## Почему так

Документация проекта разрослась до ~692 КБ в 32 файлах. Виноват жанр: журналы
писались повествованием, а оно растёт от времени работы, а не от сложности
решения, и не имеет естественного конца. Заменяем жанр на записи фиксированной
формы с лимитом. Строку в 200 символов раздуть невозможно.

## Где что живёт

| Файл                       | Что внутри                                       | Когда меняется                       |
| -------------------------- | ------------------------------------------------ | ------------------------------------ |
| `docs/PROJECT-MAP*.md`     | Как устроен проект: структура, связи, инварианты | При изменении структуры кода         |
| `docs/DECISIONS.md`        | Реестр решений: строка на решение                | При каждом принятом решении          |
| `docs/CODE-STYLE.md`       | Правила кода и комментариев                      | Редко                                |
| `docs/<версия>/PLAN.md`    | План работ и отчёт по нему                       | При смене плана и по закрытии пункта |
| `docs/<версия>/CONTEXT.md` | Суть текущего шага                               | Перезаписывается целиком каждый шаг  |

В версионной папке ровно два файла. Третьего не появляется никогда: если
материалу тесно — он либо решение (в реестр), либо устройство (в карту), либо
развёрнутое «почему» (в тело коммита).

## Тело коммита — основной носитель «почему»

Заголовок, пустая строка, 3–8 строк объяснения: что не так было, почему выбрано
это решение, что отвергнуто. Текст привязан к диффу, не устаревает и ищется
(`git log -S 'FLUSH_TIMEOUT_MS'`, `git show <хеш>`).

Однострочные сообщения вида `style: правки` обесценивают реестр: по такому хешу
копать нечего.

## Реестр решений

Одна строка, четыре поля через `·`:

```
2026-08-06 · net-check: пробы последовательно · 429 у Shikimori при веере · 5c31645
```

Дата, предмет, причина до 15 слов, хеш. Никаких абзацев и подразделов.
Отменённое решение не стирается: добавляется новая строка со словом «отменяет»
и хешем прежней.

## PLAN.md

Пункт — строка с галочкой. Закрыли пункт — ставим `[x]` и дописываем хеш в конец
строки. Отдельного отчёта нет: план с галочками и есть отчёт, и он не может
разойтись с планом.

```
- [x] 5.3.7 Сторож прокси при аварийном выходе · 5a3ea87
- [ ] 5.4 Движок фильтров вместо ручных списков
```

Подробности пункта — в коммитах пункта. В плане их нет.

## CONTEXT.md

Рабочий буфер: где остановились, что проверено, что делать следующим шагом.
Перезаписывается целиком, историю не копит. Лимит 40 строк. Пустой файл —
нормальное состояние между задачами.

## Лимиты

| Что                  | Потолок                            |
| -------------------- | ---------------------------------- |
| `PLAN.md`            | 8 КБ                               |
| `CONTEXT.md`         | 40 строк                           |
| `DECISIONS.md`       | строка на решение, до 200 символов |
| Раздел карты проекта | 1 экран                            |

Версионный файл сверх потолка — признак сползания в рассказ, а не большой
версии.

## Чего в документации не бывает

- Пересказа кода словами: код читается быстрее пересказа и не врёт.
- Размеров файлов и числа строк: устаревают от каждого коммита.
- Истории итераций «сначала сделали так, потом переделали»: это git.
- Ссылок на номера строк чужого кода и на строки монолита.
- Статусов и дат внутри текста: статус — галочка в плане, дата — в git.
- Новых файлов «на время»: временное живёт в `CONTEXT.md`.

## Как писать через API

Запись файла целиком выше ~18 КБ сплошного русского текста молча обрывается,
а API возвращает успех. Поэтому: файлы держим меньше потолка, после записи
перечитываем, а точечные правки в существующих файлах отдаём человеку строкой
для локальной вставки.
