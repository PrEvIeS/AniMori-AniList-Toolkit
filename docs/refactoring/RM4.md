# Этап 4: Сборка Desktop-приложения (Интеграция Tauri 2.0)

Цель: создание независимого исполняемого файла для Windows с внедрённым скриптом
на базе единой кодовой базы, обход сетевых ограничений браузера и обеспечение
нативного UX. Стек: Tauri 2.0, Rust, WebView2, Vite Environment Modes.

> Актуализировано на старте Этапа 4 (31 июля 2026):
> целевая платформа только Windows, macOS и Linux из плана убраны;
> добавлен условный пункт 4.11;
> контракт `IBridge` и обе реализации моста готовы с Этапа 3, писать их заново не нужно.

## 4.1. Инициализация рабочей среды Tauri

- Действие: выполнение команды `tauri init` в корне существующего Vite-проекта
  для генерации директории `src-tauri` (Rust-бэкенд).
- Конфигурация: настройка базовых параметров окна и манифеста приложения
  в `src-tauri/tauri.conf.json`, идентификатор приложения, имя продукта,
  версия из `package.json` (2.0.0).
- Ограничение: `Cargo.toml`, `Cargo.lock` и результат `tauri init` создаёт и
  коммитит разработчик локально, как и файлы npm-манифеста.

## 4.2. Интеграция системных плагинов

- Действие: установка и регистрация нативных плагинов Tauri для реализации
  контракта `IBridge`, разработанного на Этапе 3.
- Зависимости (npm-часть уже установлена на Этапе 3):
  - `@tauri-apps/plugin-http` — выполнение сетевых запросов на стороне ОС.
  - `@tauri-apps/plugin-store` — файл настроек `animori-settings.json`.
  - `@tauri-apps/plugin-clipboard-manager` — доступ к системному буферу обмена.
- Rust-часть: соответствующие крейты в `src-tauri/Cargo.toml` и регистрация
  плагинов в билдере приложения. Без регистрации вызовы из `TauriBridge`
  упадут на этапе исполнения, а не компиляции.

## 4.3. Настройка инъекции скрипта (Rust Backend)

- Действие: модификация точки входа бэкенда (`src-tauri/src/main.rs`).
- Логика:
  - Использование макроса `include_str!` для включения собранного Vite-бандла
    режима `tauri` в тело исполняемого файла на этапе компиляции.
  - Конфигурация `WindowBuilder` на запуск внешнего URL `https://anilist.co`.
  - Передача встроенного JS-кода в `.initialization_script()`, что гарантирует
    выполнение скрипта в контексте WebView до завершения загрузки DOM.
- Условие: сборка режима `tauri` должна давать чистый JS без шапки юзерскрипта
  и без обёрток `vite-plugin-monkey`.

## 4.4. Конфигурация политик безопасности (Capabilities)

- Действие: настройка разрешений в `src-tauri/capabilities/default.json`.
- Устранение CORS: явное добавление масок целевых доменов в allowlist плагина
  HTTP по фактическому списку источников из `src/api`:
  `graphql.anilist.co/*`, `shikimori.io/*`, `shikimori.rip/*`,
  `smotret-anime.com/*` (anime365), `api.animethemes.moe/*`,
  а также источник словаря из `api/dictionary.ts`.
- Разрешения плагинов: `store:default`, `clipboard-manager:allow-write-text`.
  У буфера обмена в `TauriBridge` фоллбэка нет намеренно — отсутствие
  разрешения должно падать громко.

## 4.5. Desktop UX и системная интеграция

- Маршрутизация внешних ссылок: интеграция `@tauri-apps/plugin-shell`. Внутри
  WebView разрешён переход только по доменам `anilist.co`. Клики по внешним
  ресурсам (Shikimori, RuTracker, плееры и прочее) перехватываются на уровне
  Rust-бэкенда и передаются системному процессу для открытия в браузере
  пользователя по умолчанию.
- Персистентность окна: подключение `@tauri-apps/plugin-window-state` —
  автоматическое сохранение и восстановление геометрии окна между запусками.
- Управление навигацией: слушатели глобальных событий (шорткаты и боковые
  кнопки мыши Back/Forward) с трансляцией в `history.back()` /
  `history.forward()` внутри WebView.

## 4.6. Оркестрация процесса сборки

- Действие: настройка скриптов в `package.json`.
- Мультитаргетинг: разделение команд запуска через режимы Vite
  (`--mode userscript` и `--mode tauri`). Алиас `@bridge-impl` в
  `vite.config.ts` подтягивает нужную реализацию моста в зависимости от режима;
  прикладной код импортирует мост только как `@/bridge`.
- Контроль: после каждой правки конфигурации сборки замерять число модулей и
  размер `dist/animori.user.js`. Пакеты `@tauri-apps/*` в бандле юзерскрипта
  означают, что алиас обойдён.

## 4.7. Настройка перехвата всплывающих окон (Popup Interceptor)

- Интеграция обработчика `on_new_window` в Rust-бэкенде.
- Логика: если настройка блокировки включена, попытки iframe плеера открыть
  стороннее окно пресекаются. Если выключена, новые окна передаются в плагин
  shell и открываются в системном браузере.
- Источник значения: ключ `set_block_popups` (поле `blockPlayerPopups`),
  бэкенд читает его через мост, а не хранит своё состояние.

## 4.8. Модификация CSP-заголовков (on_web_resource_request)

- Реализация перехватчика сетевых ответов от `anilist.co` на стороне Rust.
- Ослабление или удаление оригинальных заголовков `Content-Security-Policy`
  (в частности `frame-src` и `connect-src`), что позволяет WebView загружать
  фреймы Kodik и делать сторонние запросы.

## 4.9. Система автообновлений (Tauri Auto-Updater)

- Конфигурация нативного плагина обновлений Tauri.
- При запуске Rust-бэкенд опрашивает GitHub Releases репозитория. При наличии
  новой версии пользователю предлагается автообновление бинарного файла `.exe`.

## 4.10. Автоматизация сборки (GitHub Actions CI/CD)

- Настройка workflow-файла `.github/workflows/release.yml`.
- При пуше тега с версией собираются два артефакта:
  - `animori.user.js` — для публикации на GreasyFork;
  - `AniMori_Setup.exe` — Windows-инсталлятор, прикрепляется к GitHub Release
    и используется плагином автообновления.
- Сборки под macOS (`.dmg`) и Linux (`.AppImage`) из плана исключены.

## 4.11. Сетевой блокировщик рекламы уровня оболочки (условный пункт)

- Условие: берётся в работу только после того, как десктопная сборка запускается
  и ведёт себя как юзерскрипт. Если сроки поджимают — переносится дальше.
- Логика: перехват `WebResourceRequested` в Rust-бэкенде и решение о блокировке
  запроса через крейт `adblock` (движок Brave) с набором фильтров EasyList.
  Это даёт полноценную блокировку на сетевом уровне вместо снятия узлов из DOM.
- Связь с DOM-блокировщиком: `src/features/adblock` остаётся как есть и
  продолжает работать в юзерскрипте. Сетевой уровень его дополняет, а не
  заменяет.
- Управление: тот же единственный тумблер настроек, без отдельных переключателей.

Итог Этапа 4: на выходе формируется нативный Windows-инсталлятор. Приложение
работает автономно от браузера, корректно интегрируется в ОС (открытие ссылок,
управление окном), не подвержено внешним блокировкам сети и делит 100%
бизнес-логики с версией для браузера.
